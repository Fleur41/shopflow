# ShopFlow — API Specification (v1)

Status: **Draft for review** (Phase 0). Once implemented, the OpenAPI 3.1 schema generated by drf-spectacular at `/api/v1/schema/` is authoritative. This document covers conventions and the endpoint inventory.

---

## 1. Conventions

| Topic | Rule |
|---|---|
| Base path | `/api/v1/`. A breaking change means `/api/v2/`. Additive changes (new fields or endpoints) are allowed within v1. |
| Format | JSON, `snake_case`, UTF-8 |
| IDs | UUID strings |
| Money | **Decimal strings** (`"1500.00"`), always with a sibling or document-level `currency` |
| Quantities | Decimal strings (`"2"`, `"1.250"`) |
| Time | ISO 8601 with offset, returned in UTC (`2026-10-08T18:04:11Z`) |
| Tenant scope | The organization is implied by the authenticated session. **It is never sent by the client.** Store-scoped resources sit under `/stores/{store_id}/`, and the server checks `store_id` against the caller's membership. |
| Not yours | An object outside your tenant or stores returns **404**, never 403, so its existence isn't revealed |
| Writes | Financial and inventory `POST`s **require** `Idempotency-Key: <uuid>` (§3) |
| Concurrency | Mutable master data returns `version`. `PATCH` must send it (or `If-Match`); a mismatch returns `409 STALE_VERSION`. |
| Deletes | No `DELETE` on transactional resources. Master data is deactivated (`POST …/deactivate/`). |
| Pagination | List endpoints use cursor pagination: `?cursor=…&page_size=50` (max 200) → `{ "results": [...], "next": "...", "previous": "..." }`. Cursor pagination stays stable while rows are inserted. |
| Filtering / sort | Documented per endpoint, e.g. `?search=milk&category=<id>&stock_status=low&ordering=-updated_at`. Only whitelisted fields can be filtered or sorted. |
| Rate limits | `429 RATE_LIMITED` with a `Retry-After` header. Limits are in [SECURITY.md §6](SECURITY.md#6-api-protection). |

## 2. Errors: RFC 9457 problem details

`Content-Type: application/problem+json`

```json
{
  "type": "https://docs.shopflow.app/errors/insufficient-stock",
  "title": "Not enough stock",
  "status": 422,
  "code": "INSUFFICIENT_STOCK",
  "detail": "\"Milk 500ml\" only has 2 units in stock, but you tried to sell 5. Reduce the quantity or update the inventory.",
  "errors": [
    { "pointer": "/items/0/quantity", "code": "INSUFFICIENT_STOCK",
      "meta": { "product_id": "0192…", "product_name": "Milk 500ml", "available": "2", "requested": "5" } }
  ],
  "request_id": "6f1c…"
}
```

- `detail` is human-readable and safe to show to users. `code` is stable and used by clients for localization and logic.
- 5xx responses never contain stack traces or internal details, only the `request_id` for support.

Core error codes:

| HTTP | code | Meaning |
|---|---|---|
| 400 | `VALIDATION_ERROR`, `IDEMPOTENCY_KEY_REQUIRED`, `IDEMPOTENCY_KEY_INVALID` | Field-level validation failed (`errors[]`); missing or malformed `Idempotency-Key` |
| 401 | `NOT_AUTHENTICATED`, `TOKEN_EXPIRED`, `SESSION_REVOKED`, `SESSION_EXPIRED`, `INVALID_CREDENTIALS`, `DEVICE_REVOKED`, `MFA_REQUIRED` | `TOKEN_EXPIRED` → call `/auth/refresh/`. `SESSION_REVOKED`/`SESSION_EXPIRED` → sign in again. |
| 403 | `PERMISSION_DENIED`, `CSRF_FAILED`, `ORGANIZATION_REQUIRED`, `MEMBERSHIP_INACTIVE`, `ORGANIZATION_SUSPENDED`, `NOT_A_MEMBER`, `PRIVILEGE_ESCALATION`, `CANNOT_MODIFY_SELF` | `PERMISSION_DENIED` carries `errors[0].meta.permission` (the code needed). `PRIVILEGE_ESCALATION` carries the permissions or stores you don't hold. |
| 404 | `NOT_FOUND` | Missing **or** outside the caller's tenant/stores |
| 409 | `STALE_VERSION`, `ALREADY_A_MEMBER`, `LOCK_TIMEOUT` (with `Retry-After`), `PRICE_CHANGED`, `IDEMPOTENCY_IN_PROGRESS`, `LOCK_TIMEOUT`, `REFRESH_IN_PROGRESS` | Retry or re-confirm |
| 422 | `INSUFFICIENT_STOCK`, `CREDIT_LIMIT_EXCEEDED`, `PAYMENT_EXCEEDS_BALANCE`, `PRODUCT_INACTIVE`, `CUSTOMER_FROZEN`, `RETURN_EXCEEDS_SOLD`, `DISCOUNT_LIMIT_EXCEEDED`, `IDEMPOTENCY_KEY_REUSED`, `LAST_OWNER`, `SYSTEM_ROLE_IMMUTABLE`, `BUSINESS_RULE_VIOLATION` | Business rule rejected |
| 429 | `RATE_LIMITED`, `LOGIN_TEMPORARILY_LOCKED` | Both send `Retry-After` |
| 503 | `SERVICE_UNAVAILABLE` | Maintenance or dependency down |

## 3. Idempotency

```
POST /api/v1/stores/{store_id}/sales/
Idempotency-Key: 01926b3e-8a7c-7d4e-9f00-3c2b1a0e9d11
```

- **First request:** processed, and the response is stored with the key in the same DB transaction.
- **Replay** (same key, same body hash): the original status and body are returned, with the header `Idempotent-Replayed: true`.
- **Same key, different body:** `422 IDEMPOTENCY_KEY_REUSED`.
- **Duplicate in flight:** it waits for the first to commit, then replays the result. If the wait exceeds the lock timeout, the response is `409 IDEMPOTENCY_IN_PROGRESS`.
- **Business failure** (4xx): nothing is stored, so the client may fix the request and retry with the **same** key.
- Keys are retained for 30 days. Sales, payments and adjustments also carry a permanent `client_txn_id`.
- A key belongs to one user in one business, for one endpoint. Using it from another user or endpoint is `IDEMPOTENCY_KEY_REUSED`, so a key can never return someone else's response.
- Keys: 8–255 characters of letters, digits and `. _ : -`. A UUID is recommended.
- Only successful (2xx) responses are remembered.
- **Status:** the framework is implemented (Phase 1.7). Financial and inventory endpoints (Phase 2 onward) will *require* the header. `POST /stores/`, `/roles/` and `/members/` accept it optionally.

**Create sale: request**

```json
{
  "client_txn_id": "01926b3e-8a7c-7d4e-9f00-3c2b1a0e9d11",
  "occurred_at": "2026-10-08T18:04:11Z",
  "customer_id": null,
  "items": [
    { "product_id": "0192…a1", "quantity": "2", "unit_price": "80.00",
      "discount_amount": "0.00", "scanned_code": "6161100000123" },
    { "product_id": "0192…b7", "quantity": "1", "unit_price": "60.00" }
  ],
  "order_discount": "0.00",
  "tenders": [
    { "payment_method_id": "0192…c3", "amount": "220.00", "tendered": "500.00" }
  ],
  "credit_amount": "0.00",
  "notes": ""
}
```

Server-side rules:
- `items[].unit_price` is the price the client displayed. If it differs from the server price without `price_override` + `override_reason`, the response is `409 PRICE_CHANGED`, listing the current prices.
- `SUM(tenders.amount) + credit_amount` must equal the server-computed total.
- `tendered` is only meaningful for cash. Change is `tendered − amount`.
- `credit_amount > 0` needs `customer_id`, an active account, and a check against the credit limit.

**Create sale: response `201`**

```json
{
  "id": "0192…",
  "receipt_number": "MAIN-2026-000184",
  "status": "COMPLETED",
  "currency": "KES",
  "subtotal": "220.00", "discount_total": "0.00", "tax_total": "30.35", "total": "220.00",
  "amount_paid": "220.00", "amount_on_credit": "0.00", "change_given": "280.00",
  "items": [ { "line_no": 1, "product_id": "…", "product_name": "Milk 500ml", "quantity": "2",
               "unit_price": "80.00", "tax_amount": "22.07", "line_total": "160.00" } ],
  "payments": [ { "method": "CASH", "amount": "220.00" } ],
  "customer": null,
  "cashier": { "id": "…", "name": "Jane W." },
  "occurred_at": "2026-10-08T18:04:11Z"
}
```
(The example assumes tax-inclusive pricing at 16 % VAT, with tax rounded per line: 22.07 + 8.28 = 30.35. See DECISIONS Q-1.)
